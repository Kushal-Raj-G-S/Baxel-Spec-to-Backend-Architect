# Changes made in this session

This documents everything changed on top of the existing Baxel codebase, grouped by
what problem each change solves. File paths are relative to `backend/` unless noted.

## 1. Fixed two live production outages (deprecated NVIDIA models)

- **`app/services/agents/generation.py`** — `LLM_MODEL` / `LLM_REVIEW_MODEL` / `LLM_SAGE_MODEL`
  switched from `meta/llama-3.1-8b-instruct` (deprecated, HTTP 410) to `openai/gpt-oss-20b`.
  This model has hidden chain-of-thought reasoning, so every call site's `max_tokens` was
  re-tuned upward to leave room for it (400→3000 for review agents, 1200→4000 for
  anti-fragility, 5→700 for the SAGE classifier, 400→1500 for entity extraction).
- **`app/services/nlp/cloud_embedder.py`** — `NVIDIA_EMBED_MODEL` switched from the deprecated
  `nvidia/llama-nemotron-embed-1b-v2` (HTTP 410) to `nvidia/llama-nemotron-embed-vl-1b-v2`
  (same 2048 dimension, no index rebuild needed).

## 2. Fixed a cross-tenant security bug

- **`app/main.py`, `app/api/endpoints/generate.py`, `generation_service.py`** — `/api/generate`
  had no auth and a DB query (`db_session.query(ProjectModel).first()`) that grabbed ANY
  project row instead of the calling user's. Added auth and threaded `user_id` through
  properly.

## 3. Built real pricing-plan enforcement (previously didn't exist)

- **`app/api/endpoints/dashboard_api.py`** — added `PLAN_LIMITS` (free/pro/team/enterprise),
  `LEGACY_PLAN_ALIASES` for old DB codes (starter/creator/studio/growth),
  `normalize_plan_code()`, `get_user_plan()`. Enforcement added to `run_pipeline_job`
  (char + run limits) and `create_project` (project limit). Fixed a hardcoded
  `x-baxel-plan-code = "studio"` bug in the response headers.
- DB migration: `pricing_plans` table codes renamed (starter→free, creator→pro,
  studio→team); `profiles.plan_code` cascades via FK.
- **`app/api/endpoints/chat.py`** — added daily chat-quota enforcement using the same
  `get_user_plan`.

## 4. Fixed a silently-broken multi-stack codegen bug

- **`app/api/endpoints/dashboard_api.py`** — the ZIP/code-skeleton generator was hardcoded
  to Python/FastAPI regardless of the actually-chosen `tech_stack.language`. Added
  `_detect_stack_family()` / `generate_code_skeleton()` dispatcher so a TypeScript/NestJS
  spec no longer silently produces a Python export.

## 5. Built a previously non-functional feature

- **`app/api/endpoints/dashboard_api.py`** — `share_run` / `get_shared_run` were stubs;
  implemented properly.

## 6. Frontend bug fixes

- **`frontend/src/app/app/dashboard/page.tsx`**
  - Added a visible error banner — the existing `setStatus()` calls updated state that
    was never actually rendered anywhere, so failures were silently invisible to users.
  - Fixed `specBusinessRules` reading a nonexistent `result.business_rules` key (should
    read `result.rules`) and a `dbTables` variable reading a nonexistent `result.database`
    key (should read `result.entities`) — both caused "0 captured" display bugs despite
    correct backend output.
  - Added `buildSpecPayload()` so the displayed char-limit counter matches what the
    backend actually validates (previously undercounted a ~200-350 char system preamble,
    so users could see "0 left" and still get rejected).
  - Added `generationSeconds` display ("Generated by X (model) · Took Ys").

## 7. Fixed real generation-pipeline reliability bugs (found via live multi-tier testing)

All in **`app/services/agents/generation.py`**, found by running real generations across
every pricing tier with progressively larger/more complex specs:

- **Split Phase 1A/1B timeout budgets.** A single shared timeout around both phases let a
  slow Phase 1A (schema generation) starve Phase 1B's budget entirely, causing hard
  timeouts on specs that were actually close to succeeding.
- **Full-revision regression guard.** When the DBA reviewer flagged a schema issue, the
  "full revision" path regenerates the entire schema from scratch in one call — and on a
  large spec it once collapsed a 9-table schema down to 1 table while fixing the flagged
  column, still returning a 200 OK. Now: if a full revision produces *fewer* tables than
  the pre-revision spec, the revision is discarded and the pre-revision spec is kept.
- **Size-scaled Phase 1A/1B timeouts** (`_compute_phase_timeouts`) instead of one flat
  number for every spec, since latency scales with spec complexity, not a fixed cost.

## 8. Speed optimizations (verified with real before/after timing, no quality loss)

- **Chunked Phase 1A for large specs** (`_generate_database_spec_chunked`,
  `_generate_database_chunk`, `_generate_project_meta`). Large/complex specs used to run
  the entire database-schema design as ONE monolithic LLM call (250-450s+ on a large
  Enterprise-tier spec). Now, when a spec is large enough (size signal from prompt length
  or entity count), it splits into several smaller concurrent calls — one per group of
  entities — mirroring the pattern Phase 1B already used. Verified: 249s → 49s on the same
  spec, with equal-or-better output (25 tables/131 endpoints vs. 22/114 on the same input).
  Small/typical specs are completely untouched (still the original single-call path).
  - **Correctness fix #1**: if any individual chunk fails (even after its own 3 retries),
    the whole call now falls back to the single-call path instead of silently shipping a
    schema with missing tables. (Found live: a chunk hit the model's "lazy JSON
    truncation" bug and silently dropped the Project and Task tables from a
    project-management spec — the pipeline still reported success. Any chunk failure now
    means "redo the whole thing reliably," not "ship what we have.")
  - **Correctness fix #2 — a more insidious case**: a chunk call can return a schema-valid
    response that still only covers SOME of its assigned entities, with no exception
    raised at all. Found live: 2 chunks covering 12 named entities returned only 7 tables
    total, silently dropping Task, Workspace, Team, Comment, Subtask, and Notification,
    while both chunk calls reported success. Added a completeness check: a real schema
    for N named entities always has at least N tables in practice (schemas add
    junction/support tables, they don't merge named entities together), so if the merged
    result has fewer tables than named entities, that's now treated as an incomplete
    result and falls back to the single-call path. Verified live afterward: the same spec
    correctly produced 10/10 tables with all entities present.
  - **Reliability + speed fix #3**: even with the guard above, a genuinely incomplete
    chunked attempt used to fall straight back to a full single-call regeneration —
    paying for Phase 1A TWICE (a ~210s chunked attempt, then a ~230s single-call
    fallback), stretching one Enterprise-tier generation to 12m38s total. Fixed three
    ways: (1) chunk size reduced 6→4 entities so each call has less to track, (2) the
    chunk prompt now gives an explicit numbered checklist of assigned entities and
    demands the model verify full coverage before answering, (3) a failed/incomplete
    chunked attempt now gets ONE independent retry (still much faster than the
    single-call path) before falling back. Verified live on the same spec that
    previously took 12m38s: the improved prompt + smaller chunks succeeded on the first
    attempt this time, no retry or fallback needed, output correct (15 tables for 14
    named entities), total time 7m31s.
- **Overlap DevOps/Spice generation with Phase 1A on large specs.** DevOps and Spice
  generation (unlike Endpoints/BusinessRules/Resilience) only read `project_name`/
  `tech_stack` — they never touch the table list — but were waiting for the ENTIRE
  Phase 1A (schema chunks + merge) to finish before starting anyway, adding their
  ~10-40s on top of Phase 1A's own duration instead of hiding it inside it. On large
  specs (the same ones that trigger chunked Phase 1A), that metadata is already
  produced by a small, fast, independent call (`_generate_project_meta`). Now: as soon
  as that call resolves, DevOps and Spice start immediately as background tasks,
  running concurrently with the schema chunks still generating; Phase 1B later just
  gathers their already-in-flight (often already-finished) results instead of starting
  them fresh. Small/typical specs are untouched — this only activates on the same size
  threshold that triggers chunking. Verified live: Phase 1B's "starting" log only
  showed 3 fresh calls (Endpoints/BusinessRules/Resilience) instead of 5, confirming
  DevOps/Spice were already running. One run hit a Phase 1B timeout (500 error)
  immediately after an unrelated entity-extraction call took 275s (vs. its normal
  1.7s) — independent evidence the NVIDIA API was degraded at that moment. An
  identical retry succeeded cleanly seconds later with Phase 1B well under budget,
  so this was treated as transient API-side flakiness coinciding with the change,
  not a defect in it — kept live rather than reverted.
- **Tried and correctly rejected** (tested per an explicit "only if it doesn't cost
  quality" request, kept here so this isn't retried blindly later):
  - `reasoning_effort: "low"` for the Endpoints and Business Rules calls. Unlike entity
    extraction, these are real design/reasoning tasks, not simple extraction — verified
    live it cut output almost in half (57→32 endpoints, missing 9+ tables' worth of
    endpoints entirely; 18→10 business rules). Left at default reasoning.
  - Reducing DevOps `max_tokens`. 3 live samples at 8192 vs. 16384 showed no reliable
    speed trend either direction, and output completeness (env var count) already
    varied 1-8 independent of the token budget — not enough signal to call it safe.
- **GLiNER pre-warmed at server startup** (`app/main.py`) — it was only ever initialized
  lazily, mid-request, on the entity-extraction fallback path, costing ~7s of model-load
  time inside a live request. Moved to the startup pre-warm alongside the other NLP
  services. No behavior change, just moved off the request's critical path.
- **Entity extraction now uses `reasoning_effort: "low"`**
  (`app/services/nlp/entity_extractor.py`) — this is a simple 3-list JSON extraction task
  sitting fully sequential before the Architect phase even starts; it doesn't need deep
  reasoning. Verified on two different specs: 6.2s→1.7s and 12.0s→1.9s (3.6x-6.3x faster),
  extracting the *same or more* actors/entities/integrations both times, never fewer.
- **Reduced `max_tokens` for the Spice and Resilience calls** (16384 → 4096) — both have
  small, bounded outputs (3 fields; a rating + 3 scenarios + a checklist), so the old
  16384 ceiling just let the reasoning model "think" far longer than needed. A live run
  showed the Spice call alone stretching Phase 1B to ~4 minutes before failing validation
  and falling back to a default. Verified: both succeed just as reliably at 4096 and are
  2-2.5x faster (23.9s→9.5s, 45.1s→22.1s). DevOps was tested too but left unchanged — its
  output (Dockerfile + docker-compose) is genuinely large, and the one sample taken was
  actually *slower* at 4096, so it wasn't touched without stronger evidence.

## Net effect on a large/complex spec (verified, same input, before vs. after all fixes)

| | Before | After |
|---|---|---|
| Phase 1A (schema) | 249s | 49s |
| Phase 1B (endpoints/rules/devops/spice/resilience) | up to 248s (Spice fallback) | ~50s |
| Entity extraction | 6-12s | 1.7-1.9s |
| Total generation time | 7-8 min | ~4-5 min (varies with spec size and whether a revision pass triggers) |
| Output completeness | baseline | equal or more tables/endpoints on the same input |
